As an existing user, I want to log in to my Creatio CRM account using my business email and password through a secure and well-designed form and get clear error messages when I enter invalid credentials.
  • AC1
    Email — Invalid format & domain: Business Email field shall be highlighted with red and display "Invalid email format" error when the user enters an invalid email format or domain name.
  • AC2
    Email — Exceeds 400 characters: Business Email field shall be highlighted with red and display "Invalid email format" error when the user enters an email longer than 400 characters.
  • AC3
    Password — Exceeds 100 characters: Password field shall be highlighted with red and display "Invalid value. Value must contain up to 100 characters" when the user enters a password exceeding 100 characters.
  • AC4
    Invalid credentials: "Invalid email or password" error shall be displayed at the bottom of the page when the user enters an incorrect username/password combination and attempts login.
🔍 Requirement Breakdown

⚙️ Functional Requirements

  • Login form with Business Email and Password fields
  • Inline field-level validation on email format (regex)
  • Inline field-level validation on email length (> 400 chars)
  • Inline field-level validation on password length (> 100 chars)
  • Server-side authentication error at bottom of page
  • Red highlight on invalid fields
  • Specific, distinct error messages per validation rule

🚀 Non-Functional Requirements

  • Validation must be real-time / on-blur (UX expectation)
  • Error messages must be visually accessible (WCAG AA contrast)
  • Login response time < 2s under normal load
  • Error messages must not leak implementation details
  • Form must be keyboard-navigable

📐 Data & Validation Rules

  • Email max length: 400 chars (AC2)
  • Password max length: 100 chars (AC3)
  • Email format: RFC 5321 compliant + domain validation
  • Boundary values: exactly 400, exactly 401 chars for email
  • Boundary values: exactly 100, exactly 101 chars for password
  • Empty fields: behavior not specified — open question

🔒 Security Considerations

  • Generic "Invalid email or password" prevents user enumeration
  • No password content should be revealed in error messages
  • Login attempt rate limiting (not covered in AC — gap)
  • HTTPS enforcement for credential transmission
  • No sensitive data in client-side error responses
⚠️ Open Questions / Gaps
  • Are validations triggered on blur, on submit, or on keypress?
  • What error is shown for empty email or password fields?
  • Is there a CAPTCHA or lockout after N failed attempts?
  • Does the 400-char email limit apply before or after UI paste normalization?
  • What is the expected behavior when both fields are invalid simultaneously?
  • Is "remember me" / SSO in scope for this story?
  • Should the red highlight persist after error is corrected in real time?

  • 🟡
    [Clarification — High] Confirm with the dev team whether validations fire on blur or on form submit. This determines test execution sequence for all TC-NEG-* and TC-BND-* cases.
  • 🟡
    [Test Data] Pre-seed the test environment with at least 2 known valid accounts and 1 locked account before test execution begins. Coordinate with DevOps in the first week of Sprint 1.

    [Automation — Sprint 1] Prioritize automation of boundary tests (TC-BND-001 to 006) and primary negative flows (TC-NEG-001, 004, 005, 007, 008) using the existing Playwright page-object model. These are regression-critical and fast to automate given the framework already exists.
  • 🟢
    [Regression] This login form is a gateway feature. Any changes to authentication in future sprints must re-run the full TC-POS-*, TC-NEG-*, and TC-BND-* suites. Consider tagging these scenarios as @smoke and @regression in Playwright.
  • 🔵
    [Accessibility] Run axe-core scan against the login form post-implementation. Ensure all error messages use role="alert" or aria-live="polite" for screen-reader compatibility (WCAG 2.1 SC 4.1.3).
